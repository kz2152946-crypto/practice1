# Отчёт по практической №1

## 1. Вариант и масштаб

| Поле | Значение |
|---|---|
| ФИО (как в VK Education) | Зобова Ксения Павловна |
| Вариант (запрос) | Q10 «Returned Item Reporting» (вариант 2) |
| Масштаб `sfN` | sf1 |
| Почему выбрал такой масштаб | Я работаю на ноутбуке, и у Docker там всего 8 ГБ памяти на все контейнеры сразу. На sf1 в `lineitem` 6 001 215 строк (~150 МБ в Parquet+ZSTD). Этого уже хватает, чтобы разница между кодеками была видна в разы по размеру, а каждая запись или запрос занимает секунды. Весь бенчмарк (8 вариантов × запись ×2 + 2 запроса × 4 прогона с перезапусками) у меня прошёл примерно за 15 минут. На sf10 то же самое заняло бы часы, а 10 параллельных потоков упёрлись бы в память. Масштаб один и тот же на всех слоях: Bronze, Silver, Gold и бенчмарк берут `tpch.sf1`. |

## 2. Поднятые сервисы — и почему именно они

`docker ps` (полный вывод — [results/docker_ps.txt](results/docker_ps.txt)):

```
NAMES             IMAGE                                    STATUS                    PORTS
trino             trinodb/trino:476                        Up 20 seconds (healthy)   0.0.0.0:8080->8080/tcp
lakekeeper        quay.io/lakekeeper/catalog:latest-main   Up 32 seconds             0.0.0.0:8181->8181/tcp
lakehouse-pg      postgres:17                              Up 33 seconds             0.0.0.0:5433->5432/tcp
lakehouse-minio   pgsty/silo:latest                        Up 33 seconds             0.0.0.0:9000-9001->9000-9001/tcp
```

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
|---|---|---|
| MinIO (`pgsty/silo`) | S3-совместимое объектное хранилище (сюда физически падают parquet/orc-файлы) | Даёт тот же S3 API, что AWS S3, но локально и бесплатно, поэтому Trino, Spark и Lakekeeper подключаются к нему как к «настоящему» S3, и тот же стек без переделок переносится в облако. Хранилище отделено от вычислений: можно добавить второй движок (Spark), и он будет читать те же файлы. Официальные образы MinIO теперь закрыты (`quay.io/minio` отвечает 401), поэтому я взяла открытый форк Silo. Порты, переменные и консоль у него те же. |
| PostgreSQL 17 | БД, где Lakekeeper хранит метаданные каталога | Lakekeeper поддерживает именно Postgres как бэкенд. Это надёжная транзакционная БД, и она гарантирует, что смена «текущего metadata.json» у таблицы атомарна: на этом держится ACID в Iceberg. Postgres открытый, лёгкий и поднимается одной командой. Проброшен на 5433, потому что 5432 занят моим локальным Postgres. |
| Lakekeeper | Iceberg REST Catalog — каталог метаданных таблиц | REST-каталог — это стандарт Iceberg: к одному каталогу подключаются Trino, Spark, PyIceberg и другие. Hive Metastore тяжелее (Java + своя БД + Hadoop-зависимости), а Nessie заточен под git-подобные ветки, которые мне не нужны. Lakekeeper написан на Rust, это один маленький контейнер с UI, warehouse регистрируются через простой REST API. Сделала 4 warehouse: `bronze`, `silver`, `gold` и `bench` для экспериментов. |
| Trino 476 | SQL-движок: ходит в Lakekeeper за метаданными и читает/пишет данные в MinIO | Интерактивный MPP-движок, понимает обычный ANSI SQL. Его Iceberg-коннектор умеет всё, что нужно по заданию: CTAS, партиционирование, `ALTER TABLE` для эволюции схемы, `FOR VERSION/TIMESTAMP AS OF`, `rollback_to_snapshot`, системные таблицы `$files/$snapshots/$properties`. Есть встроенный коннектор `tpch`, так что данные ниоткуда не надо скачивать. По сравнению со Spark стартует мгновенно, и на малых объёмах запросы быстрее. |
| Apache Spark 3.5.3 (часть 6.2) | Второй движок: читает Bronze напрямую через Lakekeeper REST | Подробно в 6.2. Нужен, чтобы показать главное свойство lakehouse: таблицы открытые, и с ними работает не только Trino. |

### Скрипты, которыми поднимала стек

Полностью — [scripts/01_stack.sh](scripts/01_stack.sh) (запускаю `bash scripts/01_stack.sh`), ниже — главное:

```bash
# MinIO — объектное хранилище (форк silo вместо закрытого quay.io/minio). 9000 — S3 API, 9001 — консоль
docker run -d --name lakehouse-minio -p 9000:9000 -p 9001:9001 \
  -e MINIO_ROOT_USER=minioadmin -e MINIO_ROOT_PASSWORD=minioadmin \
  -v p1-minio-data:/data pgsty/silo:latest server /data --console-address ":9001"

# PostgreSQL — метаданные Lakekeeper (5433 на хосте: 5432 занят локальным Postgres)
docker run -d --name lakehouse-pg -e POSTGRES_PASSWORD=postgres -p 5433:5432 \
  -v p1-pg-data:/var/lib/postgresql/data postgres:17

# Lakekeeper — сначала миграции БД (одноразово), потом сам REST-каталог на 8181
docker run --rm -e 'LAKEKEEPER__PG_ENCRYPTION_KEY=This-is-NOT-Secure!' \
  -e 'LAKEKEEPER__PG_DATABASE_URL_READ=postgresql://postgres:postgres@host.docker.internal:5433/postgres' \
  -e 'LAKEKEEPER__PG_DATABASE_URL_WRITE=postgresql://postgres:postgres@host.docker.internal:5433/postgres' \
  quay.io/lakekeeper/catalog:latest-main migrate
docker run -d --name lakekeeper -p 8181:8181 -e 'LAKEKEEPER__PG_ENCRYPTION_KEY=This-is-NOT-Secure!' \
  -e 'LAKEKEEPER__PG_DATABASE_URL_READ=postgresql://postgres:postgres@host.docker.internal:5433/postgres' \
  -e 'LAKEKEEPER__PG_DATABASE_URL_WRITE=postgresql://postgres:postgres@host.docker.internal:5433/postgres' \
  quay.io/lakekeeper/catalog:latest-main serve

# бакеты bronze/silver/gold/bench через клиент mc (форк pgsty/mc)
docker run --rm --entrypoint /bin/sh --add-host host.docker.internal:host-gateway pgsty/mc:latest -c \
  "mc alias set m http://host.docker.internal:9000 minioadmin minioadmin && for b in bronze silver gold bench; do mc mb --ignore-existing m/\$b; done"

# принять Terms of Use и зарегистрировать warehouse (json-ы в scripts/create-warehouse-*.json)
curl -X POST http://localhost:8181/management/v1/bootstrap -H "Content-Type: application/json" -d '{"accept-terms-of-use": true}'
for w in bronze silver gold bench; do
  curl -X POST http://localhost:8181/management/v1/warehouse -H "Content-Type: application/json" -d @scripts/create-warehouse-$w.json
done

# Trino — монтирую папку catalog/ целиком: bronze/silver/gold/bench.properties (iceberg) + tpch.properties
docker run -d --name trino -p 8080:8080 -v "$(pwd)/catalog:/etc/trino/catalog" trinodb/trino:476
```

`SHOW CATALOGS` → `bench, bronze, gold, silver, system, tpch` ([results/show_catalogs.txt](results/show_catalogs.txt)).

## 3. Разбор запроса — какие данные нужны

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |
|---|---|---|
| `orders` | `orderkey`, `custkey`, `orderdate` | **Фильтр** по `orderdate` в [1993-10-01, 1994-01-01), **джойн** с lineitem по `orderkey` и с customer по `custkey` |
| `lineitem` | `orderkey`, `returnflag`, `extendedprice`, `discount` | **Фильтр** `returnflag = 'R'`, **джойн** по `orderkey`, **агрегат** `sum(extendedprice * (1 - discount))` = выручка |
| `customer` | `custkey`, `name`, `acctbal`, `address`, `phone`, `comment`, `nationkey` | **Джойн** по `custkey` и `nationkey`, **группировка** и **вывод** всех этих полей |
| `nation` | `nationkey`, `name` | **Джойн** по `nationkey`, **вывод** названия страны |

Итог: топ-20 клиентов, `ORDER BY revenue DESC LIMIT 20`. Самая тяжёлая часть — скан `lineitem` (6 млн строк) и её джойн с отфильтрованными заказами (за Q4 1993 ~57 тыс. заказов).

## 4. Медальон — решения по каждому слою

Все цифры — из [results/layers_stats.csv](results/layers_stats.csv) (запрос [sql/00_layer_stats.sql](sql/00_layer_stats.sql): `count(*)`, размер — `sum(file_size_in_bytes)` из `"$files"`, кодек — из `"$properties"`).

Общие решения для всех слоёв:
- **Формат PARQUET.** Колоночный формат, и Trino читает из файла только нужные колонки. Например, Q10 из 18 колонок lineitem берёт 4. Parquet — стандарт экосистемы: его без проблем читают и Trino, и Spark (проверила в 6.2). ORC в моём бенчмарке получился не лучше (раздел 5), а NONE в ORC оказался даже на 20% тяжелее Parquet.
- **Сжатие ZSTD.** По бенчмарку ZSTD почти такой же компактный, как GZIP (lineitem 147.3 против 143.7 МБ, +2.5%), но пишется быстрее (16.9 с против 21.4 с). По скорости запросов он не хуже остальных. SNAPPY на 35% тяжелее при той же скорости чтения, NONE в 2.4 раза тяжелее.
- Кодек задаю через `SET SESSION <каталог>.compression_codec = 'ZSTD'`, а в `$properties` таблицы он виден как `write.parquet.compression-codec = zstd`.

**Почему срез Q4 1993 + `R` я сделала в Gold, а не в Silver.** Silver — это общий очищенный слой. Если его отфильтровать под один запрос, он станет бесполезен для любого другого (например, Q3 по другим датам). А партиционирование по месяцу даёт почти ту же скорость, что готовый срез: читаются только 3 месяца.

## 5. Тесты производительности

### Как мерила

Скрипт [scripts/benchmark.py](scripts/benchmark.py), SQL одного варианта — [sql/04_benchmark.sql](sql/04_benchmark.sql). Сырые замеры: [results/benchmark.csv](results/benchmark.csv) (264 замера), сводка: [results/benchmark_summary.csv](results/benchmark_summary.csv).

- Пересоздала Bronze (`lineitem`, `orders`, плюс `customer` и `nation`, чтобы Q10 целиком шёл по одному варианту) в отдельной схеме `bench.<формат>_<кодек>`: 2 формата × 4 кодека = 8 вариантов. Партиционирование как в Bronze (`orders` по `year(orderdate)`). Кодек задаётся через `SET SESSION bench.compression_codec`, а в `$properties` проверила, что он действительно записался (`zstd`, `gzip`, `snappy`, `none`; для ORC GZIP пишется как `zlib`).
- **Размер:** `sum(file_size_in_bytes)` из `"$files"`.
- **Время записи:** `CREATE TABLE ... AS SELECT * FROM tpch.sf1.*` через `docker exec trino trino --execute` (как `time`), 2 прогона, в таблице лучший.
- **Время запросов:** мой Q10 и агрегация Q1 по всей lineitem из гайда 3. **cold** — сразу после `docker restart trino lakehouse-minio`, **warm** — медиана трёх следующих прогонов. Время двух видов: «стена» (как у `time`, включает старт CLI ~1 с) и `exec_ms` из `system.runtime.queries`. Каждый запрос помечала через `--source`, чтобы его там найти.
- Железо: MacBook, Docker Desktop, 10 CPU, 8 ГБ RAM на Docker.

Подходит для архива, который пишут один раз и читают редко. |
| ZSTD | cold 4.75 с / warm 1.86 с (exec 1.08 с) | 190.75 (lineitem 147.27) | Всего на 2.5% больше GZIP (−58.6% от NONE), а пишется на 21% быстрее GZIP (16.9 с). На warm-прогонах у ZSTD самый маленький `exec_ms` на Q10 (1084 мс) и самый быстрый Q1 (1.04 с), но отрыв небольшой (см. п. 3 ниже). **Выбрала ZSTD для всех слоёв**: размер почти как у GZIP, скорость как у быстрых кодеков. |

### Что я из этого поняла

1. **Размер — самый чёткий результат.** Без сжатия lineitem занимает 355 МБ (Parquet) и 432 МБ (ORC). SNAPPY срезает 44–51%, GZIP и ZSTD — 59–66%. GZIP и ZSTD почти одинаковые: разница 2–3%. Parquet и ORC со сжатием тоже почти сравнялись (ZSTD: 147 против 154 МБ). Без сжатия ORC заметно толще, на 21%.
2. **Запись.** Быстрее всех `parquet_none` (12.7 с), дольше всех GZIP (21.4 с в Parquet). Как и ожидалось: сильнее жмёшь — больше CPU. В ORC разница меньше (16–19 с), и вообще ORC в Trino у меня писался медленнее Parquet. Важная оговорка: время записи на sf1 включает генерацию данных коннектором `tpch`, и между двумя прогонами одного варианта разброс доходил до 5 с (например, `parquet_none` lineitem: 12.7 и 18.2 с). Поэтому надёжно видно только «GZIP медленнее всех», а порядок SNAPPY/ZSTD/NONE внутри шума.
3. **Чтение.** На sf1 весь Q10 выполняется за 1–3 с, и **разница между кодеками сравнима с шумом**: cold у всех 4.0–5.0 с, warm 1.8–2.7 с. Честно: по своим цифрам я не могу сказать, что какой-то кодек ускоряет мой запрос. Единственный явный выброс — `orc_none` на Q1 cold, 6.4 с против 2.2–3.4 с у остальных: ему пришлось читать с диска 432 МБ вместо ~150. Это ответ на вопрос из гайда, почему NONE не всегда самый быстрый на чтение: байтов с диска больше, а распаковка ZSTD/SNAPPY стоит дешевле, чем чтение лишних байтов.
4. **Cold vs warm.** Warm-прогоны в 1.5–2.5 раза быстрее cold: после рестарта Trino заново грузит метаданные Iceberg из Lakekeeper/MinIO и прогревает JIT, а MinIO заново читает файлы с диска. `exec_ms` из `system.runtime.queries` примерно на 1–1.5 с меньше «стены», потому что «стена» включает старт CLI и `docker exec`. Если сравнивать один прогон без перезапуска, можно случайно сравнить тёплый вариант с холодным.
5. **Чтобы различия в чтении стали видны**, нужен sf10+: там данные перестают помещаться в кэш, и объём байтов с диска начинает решать. На sf1 выбор кодека в основном вопрос **места и времени записи**. По этим двум метрикам ZSTD — лучший компромисс, GZIP — для холодного архива, SNAPPY/NONE не дают выигрыша, который оправдал бы лишние 35–140% места.

Метаданные: манифест lineitem — 1 файл на 9.6 КБ (`parquet_zstd`) и 9.0 КБ (`orc_none`) на фоне 147–432 МБ данных ([results/metadata_size.txt](results/metadata_size.txt)), то есть накладные расходы Iceberg ничтожны. У всех вариантов lineitem по 8 файлов, так что число файлов на время не влияло.

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Твой ответ  |
|---|---|
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | Обычная БД (Postgres) хранит данные и считает на одной машине: когда данных десятки терабайт, она упирается в диск и CPU одного сервера, и масштабировать её дорого. Классическое DWH (Teradata, Vertica) масштабируется, но данные лежат в закрытом формате внутри него, и платишь за хранение и вычисления вместе. Data lake (просто файлы в S3) дешёвый и бесконечный, но там нет транзакций, схемы и истории: легко получить «болото» из файлов, про которые никто не знает, что в них. **Lakehouse объединяет плюсы**: данные лежат дёшево в объектном хранилище (MinIO/S3) в открытых форматах (Parquet), а табличный формат Iceberg + каталог дают то, что было только в DWH: ACID-транзакции, схему и её эволюцию, снапшоты и time travel, статистику для оптимизатора. Хранение и вычисления разделены: в моей работе одни и те же файлы Bronze читали и Trino, и Spark, без копирования. Вычисления масштабируются отдельно от хранения, и не нужно держать данные в каком-то одном движке. |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | SQL: [sql/05_schema_evolution.sql](sql/05_schema_evolution.sql), вывод: [results/schema_evolution.txt](results/schema_evolution.txt), [results/schema_evolution_metadata.txt](results/schema_evolution_metadata.txt). Делала на копии Silver-таблицы `silver.lakehouse.dim_customer_evo` (150 000 строк, 1 parquet-файл), чтобы переименование не сломало сборку Gold. Выполнила три изменения: `ADD COLUMN loyalty_tier varchar`, `RENAME COLUMN market_segment TO segment`, `ALTER COLUMN acct_balance SET DATA TYPE decimal(16,2)` (было `decimal(12,2)`). **Что произошло:** (1) все три `ALTER` прошли мгновенно, и **файл данных не переписывался**: в `$files` до и после тот же один файл `...a5bfa738...parquet`, 150 000 строк, тот же размер. (2) **Новых снапшотов нет**: в `$snapshots` по-прежнему один `append`, а в `$metadata_log_entries` добавились новые `metadata.json`. Схема — это метаданные, данные не трогаются. (3) В `metadata.json` (достала из MinIO) видно, что **колонки идентифицируются по ID, а не по имени**: `schema 0: 1:customer_key, 2:customer_name, 3:acct_balance:decimal(12,2), 4:market_segment, 5:nation_name` → `schema 3: …, 3:acct_balance:decimal(16,2), 4:segment, 5:nation_name, 6:loyalty_tier`. После переименования колонка осталась с ID 4, поэтому старый файл, где она записана как «4», читается под новым именем `segment`. Новая колонка получила новый ID 6, которого в старом файле нет. (4) После вставки новой строки старые 150 000 строк имеют `loyalty_tier = NULL` (`count(loyalty_tier) = 1` из 150 001), `segment` заполнен у всех 150 001. Новая строка легла **отдельным новым файлом**, старый остался как был. (5) Чтение первого снапшота через `FOR VERSION AS OF` Trino делает **по схеме того снапшота**: там колонка ещё называется `market_segment`, `loyalty_tier` нет, а `acct_balance` имеет тип `decimal(12,2)`. Сначала я ошибочно написала запрос с новыми именами, и он упал с `Column 'loyalty_tier' cannot be resolved`. Так я и поняла, как это работает. |
| Пример скрипта восстановления данных из снапшота (time travel) | SQL: [sql/06_time_travel.sql](sql/06_time_travel.sql), запуск: [scripts/time_travel.sh](scripts/time_travel.sh) (подставляет id «хорошего» снапшота и время), вывод: [results/time_travel.txt](results/time_travel.txt). Таблица `silver.lakehouse.dim_customer`: 150 000 строк, `sum(acct_balance) = 674 326 849.74`, «хороший» снапшот `5794582351266468250`. **Авария:** `DELETE ... WHERE nation_name = 'JAPAN'` (−5 948 строк) и `UPDATE ... SET acct_balance = 0 WHERE nation_name = 'GERMANY'` (5 908 строк) → 144 052 строки, сумма 621 121 572.74. В `$snapshots` появились `delete` и `overwrite` с `added-position-deletes` = 5948 и 5908: Trino не переписывает файлы, а дописывает delete-файлы с номерами удалённых строк. **Чтение прошлого:** `SELECT ... FOR VERSION AS OF 5794582351266468250` и `FOR TIMESTAMP AS OF TIMESTAMP '2026-10-16 21:23:39.849 UTC'` оба вернули 150 000 строк и 674 326 849.74. **Восстановление способ 1 (точечно):** `DELETE` испорченных немецких строк + `INSERT INTO dim_customer SELECT * FROM dim_customer FOR VERSION AS OF <good> WHERE nation_name IN ('JAPAN','GERMANY')` → 150 000 строк, сумма как была, `EXCEPT` текущей таблицы с хорошей версией в обе стороны = 0 / 0. Так можно вернуть только пострадавшее, не трогая чужие изменения, сделанные после аварии. **Способ 2 (откат целиком):** снова «сломала» (`DELETE WHERE customer_key <= 1000` → 149 000) и выполнила `ALTER TABLE silver.lakehouse.dim_customer EXECUTE rollback_to_snapshot(5794582351266468250)` → 150 000 строк, сумма 674 326 849.74. В Trino 476 это работает, синтаксис именно `ALTER TABLE ... EXECUTE rollback_to_snapshot(id)`. Rollback новый снапшот не создаёт, он передвигает указатель «текущий снапшот» на старый: в `$history` у `5794…` `is_current_ancestor = true`, у всех «аварийных» — `false`. Отсюда грабля, на которую я наступила: после отката «последний по времени» снапшот — испорченный, поэтому текущий надо брать из `$history` (`is_current_ancestor`), а не `ORDER BY committed_at DESC`. Ещё честно: первый прогон скрипта упал посередине из-за моей ошибки в запросе к `summary`, когда таблица уже была испорчена. Я восстановила её тем же `rollback_to_snapshot`, поэтому в истории видно две «аварии». |

### 6.2. Подключить инструмент к lakehouse

| Инструмент | Почему выбрал именно его |
|---|---|
| **Apache Spark 3.5.3** (движок) + Iceberg 1.7.1 | Мне хотелось показать главное свойство lakehouse: таблицы открытые, и с ними работает **другой движок напрямую**, а не через Trino. Spark сам ходит в Lakekeeper по Iceberg REST и сам читает parquet из MinIO. Superset или Metabase просто ходили бы через Trino и показали бы только BI-надстройку. Spark — стандарт для тяжёлых ETL-пайплайнов, у него лучшая поддержка Iceberg (все процедуры обслуживания: `rewrite_data_files`, `expire_snapshots` и т.д.), и он масштабируется на кластер. Doris/StarRocks тоже умеют Iceberg, но это отдельная MPP-СУБД с FE/BE-узлами, тяжелее для ноутбука. Для моей задачи (интерактивный Q10 на sf1) Trino быстрее (см. ниже), так что Spark здесь — второй движок для пакетной обработки поверх тех же данных. |

**Развёртывание** — [scripts/03_spark.sh](scripts/03_spark.sh), конфиг — [spark/conf/spark-defaults.conf](spark/conf/spark-defaults.conf):

```bash
# jar'ы Iceberg один раз качаются в spark/jars (не в git)
curl -fsSL -o spark/jars/iceberg-spark-runtime-3.5_2.12-1.7.1.jar https://repo1.maven.org/maven2/org/apache/iceberg/iceberg-spark-runtime-3.5_2.12/1.7.1/iceberg-spark-runtime-3.5_2.12-1.7.1.jar
curl -fsSL -o spark/jars/iceberg-aws-bundle-1.7.1.jar https://repo1.maven.org/maven2/org/apache/iceberg/iceberg-aws-bundle/1.7.1/iceberg-aws-bundle-1.7.1.jar

# Spark в Docker: конфиг и jar'ы монтирую отдельными папками (jar'ы НЕ в /opt/spark/jars)
docker run --rm --add-host host.docker.internal:host-gateway \
  -v "$(pwd)/spark/conf:/opt/spark/conf" \
  -v "$(pwd)/spark/jars:/opt/spark/iceberg-jars" \
  -v "$(pwd)/spark:/opt/spark/work" \
  apache/spark:3.5.3 /opt/spark/bin/spark-sql -f /opt/spark/work/bronze_spark.sql
```

Ключевое в конфиге — каталог `bronze` указывает на тот же Lakekeeper и тот же warehouse:

```properties
spark.sql.catalog.bronze               org.apache.iceberg.spark.SparkCatalog
spark.sql.catalog.bronze.catalog-impl  org.apache.iceberg.rest.RESTCatalog
spark.sql.catalog.bronze.uri           http://host.docker.internal:8181/catalog
spark.sql.catalog.bronze.warehouse     bronze
spark.sql.catalog.bronze.io-impl       org.apache.iceberg.aws.s3.S3FileIO
spark.sql.catalog.bronze.s3.endpoint   http://host.docker.internal:9000
```

**Мои действия и что увидела** ([spark/bronze_spark.sql](spark/bronze_spark.sql), вывод — [results/spark_bronze.txt](results/spark_bronze.txt)):

1. `SHOW NAMESPACES IN bronze` → `lakehouse`; `SHOW TABLES IN bronze.lakehouse` → `nation, customer, orders, lineitem`. Spark увидел таблицы, которые создал Trino.
2. `DESCRIBE bronze.lakehouse.lineitem` → все 18 колонок, включая мои `loaded_at` и `source`.
3. `count(*)` по всем таблицам: 25 / 150 000 / 1 500 000 / 6 001 215, совпадает с Trino.
4. Метаданные Iceberg из Spark: `bronze.lakehouse.lineitem.snapshots` → 1 снапшот `append`; `.files` → 8 файлов, 154 835 432 байта. **Ровно столько же, сколько `"$files"` в Trino**, потому что это одни и те же файлы.
5. Простой запрос — возвраты по годам заказа (lineitem ⋈ orders, `returnflag = 'R'`): 1992 — 453 818 строк, 1993 — 454 138, 1994 — 455 521, 1995 — 115 393. Посчитал за 3.9 с.
6. Мой Q10 прямо по Bronze → **те же 20 клиентов и та же выручка, что в Gold** (57040 — 734235.2455, …, 23431 — 554269.536), за 2.4 с.

**Бонус: 10 потоков и Trino vs Spark** ([scripts/04_parallel.sh](scripts/04_parallel.sh), [results/parallel_trino.txt](results/parallel_trino.txt), [results/parallel_spark_streams1.txt](results/parallel_spark_streams1.txt), [results/parallel_spark_streams10.txt](results/parallel_spark_streams10.txt), csv Spark — `results/spark_q10_streams*.csv`). Один и тот же Q10 по Bronze, каждый поток выполняет его 3 раза. Для Spark — драйвер `tpch_run.py` из laba2, в который я добавила параметры `--catalog/--database`.

| Движок | Режим | Запросов | Общее время, с | Пропускная способность, запр/с | Время одного запроса (медиана), с |
|---|---|---|---|---|---|
| Trino | 1 поток | 3 | 5.80 | 0.52 | 1.05 (`exec_ms`) |
| Trino | 10 потоков | 30 | 24.40 | 1.23 | 4.42 |
| Spark | 1 поток | 3 | 7.55 | 0.40 | 1.43 (первый, холодный — 4.89) |
| Spark | 10 потоков | 30 | 51.81 | 0.58 | 12.22 |

Что вижу: при 10 потоках **суммарная пропускная способность выросла** (Trino в 2.4 раза, Spark в 1.45 раза), но **каждый запрос стал медленнее** (Trino в ~4 раза, Spark в ~8.5 раза). Все потоки делят одни и те же ядра и память Docker. На одиночном запросе Trino быстрее Spark (1.05 против 1.43 с), а под нагрузкой разрыв ещё больше. Ещё Spark платит «налог на старт»: первый запрос 4.9 с, а запуск JVM и SparkSession в этот замер вообще не входит. Вывод: для интерактивной аналитики на моём объёме Trino лучше, а Spark стоит брать для больших пакетных ETL, где старт окупается.

## 7. Выводы

Медальон оказался удобен тем, что у каждого слоя своя задача. В Bronze я храню сырьё один в один, поэтому всегда могу пересобрать всё заново. В Silver один раз чищу и обогащаю данные, и здесь реально нашлись грязные адреса и комментарии с пробелами. В Gold лежит готовый ответ из 20 строк, он читается за ~50 мс вместо ~1 с, и я проверила его на совпадение с эталонным запросом. По хранению главное для меня: колоночный Parquet + ZSTD дают в 2.4 раза меньше места, чем без сжатия, почти как GZIP, но пишутся заметно быстрее GZIP. На sf1 кодек на скорость запросов почти не влияет, поэтому решают место и время записи. Партиционирование надо подбирать под фильтр запроса и объём: `month(order_date)` в Silver дал чтение 3 партиций вместо 80, а для маленьких таблиц партиции только плодят файлы. Iceberg поверх объектного хранилища дал то, чего нет в «просто файлах»: эволюцию схемы без переписывания данных, снапшоты и откат после «аварии», и возможность читать те же таблицы вторым движком (Spark) без копирования.
